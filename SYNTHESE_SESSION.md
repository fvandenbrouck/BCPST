13. **Rendu LaTeX des formules (KaTeX)** (2026-08-03), demande explicite de l'utilisateur. Choix technique : **KaTeX** plutôt que MathJax (plus léger, pas de build, cohérent avec un site 100% statique). Infrastructure :
    - Nouveau fichier [`assets/js/math-render.js`](assets/js/math-render.js) : expose `MathRender.render(container)`, qui appelle `renderMathInElement` (extension auto-render de KaTeX) si elle est chargée. Ne fait rien si KaTeX n'est pas présent sur la page (safe no-op).
    - KaTeX (CSS + `katex.min.js` + `contrib/auto-render.min.js`) chargé via CDN jsdelivr (`katex@0.16.11`), **en `<head>`, sans `async`/`defer`** : ça bloque volontairement le parsing le temps du chargement, pour garantir que `window.renderMathInElement` existe déjà quand les scripts du `<body>` s'exécutent — pas de gestion de promesse/race condition nécessaire.
    - `MathRender.render(...)` appelé à la fin de chaque fonction `render()` qui fait un `target.innerHTML = html` : dans `module-page.js` (`renderShell` et `renderCours`), `qcm-engine.js`, `flashcards-engine.js`, `mindmap-engine.js`. **`carnet-engine.js` n'y touche pas** (pas de contenu mathématique dans le carnet de terrain, inutile d'y charger KaTeX).
    - **Convention d'écriture** : `$...$` pour une formule en ligne, `$$...$$` pour une formule isolée, directement dans les chaînes de texte des données de module (`paragraphs`, `bullets`, `bridge.from/to`, `q`, `options`, `hint`, `recto`/`verso`, labels de `mindmapModel`). Ces chaînes passent déjà par `esc()` (échappement HTML) avant insertion — sans risque pour les délimiteurs `$` ni les commandes LaTeX (`\`, `^`, `_`, `{`, `}` ne sont pas touchés par `esc()`).
    - Isotopes en exposant : écrire `^{87}\text{Rb}` plutôt que `87Rb` en LaTeX quand la notation apparaît dans une équation ; garder `87Rb` en texte simple dans la prose courante (pas la peine de tout mettre en LaTeX, seulement les vraies formules/équations).
    - Nombres décimaux français dans une formule : utiliser `0{,}700` (pas `0,700` ni `0.700`) pour que la virgule ne soit pas interprétée comme séparateur de liste par KaTeX.
    - **Déjà appliqué à Ch.6** (fiche Zoom, ses flashcards, son QCM, sa branche de carte mentale, `bridge`). Ch.5 et Ch.7 chargent aussi KaTeX pour rester cohérents (aucune formule actuellement, mais prêt si un futur ajout en a besoin) — vérifié : aucune régression, aucune erreur console.
    - **Pour tout futur module (SVT, PC, Maths)** : inclure le même boilerplate `<head>` (KaTeX CDN) + `<script src="../assets/js/math-render.js">` juste après `storage.js`. PC et Maths en auront un usage massif (analyse dimensionnelle, cinétique, fonctions, dérivées...).

**Comment fonctionne une page module :** chaque fichier `svt/chXX-....html` définit un objet JS `MODULE` (données pures : fiches de cours, flashcards, questions QCM, carte mentale modèle) puis appelle `ModulePage.init(MODULE)`. Le contrat de données exact est documenté en commentaire de tête dans chaque fichier `*-engine.js`. Pour un exemple de référence complet, voir [`svt/ch06-datation-absolue.html`](svt/ch06-datation-absolue.html).

**Important pour Phase 2/3 (PC, Maths) :** le gabarit à 4 onglets change de contenu selon la matière (cf. cahier des charges §3.2 et §4.2) : PC remplace Flashcards par "Applications numériques" (réponse numérique + tolérance), Maths remplace QCM par "Entraînement calculatoire" et Flashcards par "Cartes-méthode", avec un vocabulaire technique/compréhension au lieu de connaissance/raisonnement. **Le volet PC est fait, stable et éprouvé sur les 9 modules de la Phase 2, désormais intégralement terminée** (cf. décision #19, `applications-engine.js` + extensions rétrocompatibles de `module-page.js`/`qcm-engine.js`) — réutilisable tel quel pour tout futur module PC (ex. approfondissements BCPST1), pas besoin de généraliser à nouveau. **Le volet Maths (Entraînement calculatoire, Cartes-méthode, vocabulaire technique/compréhension) n'est pas encore implémenté** — à traiter selon le même principe (détection de champ sur `MODULE`, pas de flag de matière explicite) quand le premier module Maths sera attaqué concrètement, pas avant. **La Phase 3 (Mathématiques) n'a pas démarré** : aucun fichier `maths/*.html`, aucune décision de scope prise avec l'utilisateur au-delà de ce qui figure déjà dans `CAHIER_DES_CHARGES.md` §4.

**Champ `fiche.images` (optionnel, ajouté en décision #23) :** une fiche de cours (`MODULE.fiches[i]`) peut désormais porter `images:[{src, alt, credit?}, ...]`, rendu par `module-page.js` (fonction `renderCours`) sous forme de `<figure class="q-figure">` après les puces de la fiche, dans l'ordre du tableau — même contrat que `question.image` du QCM (`credit` obligatoire pour toute image sous licence externe, omis pour un schéma original dessiné pour le site). Utilisé pour l'instant uniquement par `physique-chimie/condensateur.html` (schémas loi des nœuds/mailles et circuits RC). Extension vérifiée rétrocompatible : les modules sans ce champ (ex. `chimie.html`) s'affichent à l'identique.

## 6. Conventions et consignes utiles pour la suite

- **Droit d'auteur** : ne jamais recopier le texte du manuel Belin Éducation ni d'autres sources protégées ; renvois de page en index uniquement (cahier des charges §0.1).
- **Ton des diagnostics** : toujours encourageant, jamais culpabilisant (§0.2) — les 4 paliers déjà rédigés dans `qcm-engine.js` (`buildDiagnostic`) servent de modèle de ton à reproduire pour les futurs modules.
- **Articulation Première → Terminale → BCPST1** : toujours présente en tête de module (bloc "Déjà vu / En BCPST1", champ `MODULE.bridge` dans le contrat de données).
- **Carte mentale** : jamais de modèle pré-rempli affiché par défaut, l'élève construit d'abord de mémoire (déjà respecté par `mindmap-engine.js`, ne pas changer ce comportement).
- **QCM** : ne pas se soucier manuellement de la position de la bonne réponse dans les données (`correct: <index>`) — le moteur mélange l'affichage automatiquement (cf. décision #5). Continuer de viser ≥10 questions connaissance + ≥5 raisonnement avec indice de méthode (jamais la réponse).
- **Actions sensibles** : avant de committer/pousser sur GitHub, ou de changer un réglage de dépôt (comme activer Pages), demander confirmation — sauf instruction déjà donnée explicitement en session (ex. décision #4 ci-dessus, qui autorise l'activation de Pages *à la fin de la Phase 1*, sans redemander à ce moment précis).
- **`references/`** ne doit jamais être poussé sur GitHub (gitignoré) — vérifier `git status` avant tout commit si des fichiers y ont été ajoutés/modifiés.
- **Tester dans le navigateur** avant de considérer un module terminé : ouvrir le fichier, tester les 4 onglets, vérifier l'absence d'erreur console, vérifier que le score QCM se calcule juste, puis vider `localStorage` (données de test) avant de committer.
- **Carnet de terrain** : ne jamais lui ajouter de score ni de correction automatique — c'est le principe fondateur de ce type de module (cf. §5, `CARNET_DE_TERRAIN.md` §1.3). Ne pas le fusionner avec `modules-registry.js`/`progress-gauge.js` (registre des modules notés) : il vit à part, lié depuis `index.html` par une simple carte de navigation.
- **Répétition espacée / autoexplication (cf. décision #17)** : mécanismes déjà implémentés au niveau des moteurs partagés, valables pour tous les modules sans rien ajouter dans les fichiers `svt/*.html` — ne pas réinventer ni dupliquer dans un futur module. Si Phase 2/3 (PC, Maths) ajoute un nouvel onglet (Applications numériques, Entraînement calculatoire), vérifier d'abord si la même logique de planification par date peut s'y brancher plutôt que d'en écrire une nouvelle.
- **Notation vectorielle en texte brut (cf. décision #27)** : ne jamais utiliser le caractère Unicode combinant U+20D7 (`⃗`) dans une chaîne destinée à s'afficher telle quelle (QCM `q`/`options`/`hint`, labels de carte mentale) — il produit des glyphes cassés hors contexte KaTeX. Pour un vecteur dans le Cours, utiliser `\vec{...}` en KaTeX (`$\vec{a}$`), qui fonctionne parfaitement ; pour un vecteur en texte brut, écrire simplement le nom de la grandeur sans annotation (`a`, `F`, `v0`).
- **Avant de redessiner un schéma fourni par l'utilisateur en PDF (cf. décisions #24/#25)** : si le PDF est généré depuis LaTeX/circuitikz et que le `.tex` source est disponible, lire directement les coordonnées dans le `.tex` (bien plus fiable). Sinon, extraire le SVG vectoriel exact via `pdftocairo -svg` (poppler, `brew install poppler` si absent — peut nécessiter `brew unlink xpdf` en cas de conflit, réversible) puis décoder les `<path>`/`<text>` à la main plutôt que de redessiner à l'œil.
